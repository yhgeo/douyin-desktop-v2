# 接口笔记

> 全部结论来自 2026-10-21 的实测，不是推测。
> 每条都标了怎么复现——接口会变，能复现才修得动。

---

## 一、整体链路

```
POST ttwid.bytedance.com          → 拿 ttwid（设备标识，不用登录）
本地生成 s_v_web_id                → 指纹 ID
GET  /aweme/v1/web/module/feed/   → 推荐列表（a_bogus 签名）
GET  /aweme/v1/play/?video_id=... → 302 到 CDN，返回 MP4 字节流
mpv --wid=<子窗口> 播放            → 解码出画面
```

复现：`dotnet run --project src/DouyinDesktop.Probe`

---

## 二、凭据

| 凭据 | 怎么来 | 说明 |
| --- | --- | --- |
| `ttwid` | POST `https://ttwid.bytedance.com/ttwid/union/register/`，从 `Set-Cookie` 里取 | 匿名注册，不需要登录。约 460ms |
| `s_v_web_id` | 本地生成，格式 `verify_{时间36进制}_{8位}_{4位}_4{3位}_{4位}_{12位}` | 纯随机，服务端不校验具体值 |
| `msToken` | **空着也能用** | 服务端会在响应头 `X-Ms-Token` 下发，捡到就存 |

**结论：不需要移植 368 行的 msToken 算法。** 原以为这是必需项，实测服务端根本不校验。

凭据落盘在 `%LOCALAPPDATA%\DouyinDesktop\session.json`，冷启动省掉注册往返。
超过 7 天会重新注册，避免长期用同一个设备号。

## 三、推荐流

```
GET https://www.douyin.com/aweme/v1/web/module/feed/?{params}&a_bogus={sig}&verifyFp=...
```

### 坑 1：`aweme_list` 是空的

真实数据在 `cards[].aweme`，而且 **`aweme` 是 JSON 字符串，需要二次解析**。

直接抄 `DouYin_Spider` 的解析会拿到空列表。`cards` 里没有 `aweme` 字段的是广告位/提示位，跳过。

### 坑 2：参数顺序敏感

`a_bogus` 算的是原始 query 串。参数顺序一变签名就对不上，
所以 `DeviceProfile.FeedParams` 里的顺序是照抄网页端的，别"整理"。

### 坑 3：翻页去重靠 `presented_ids`

传已展示过的 id 逗号分隔，服务端会避开。实测新一批 10 条重复 0 条。
`refresh_index` 每次递增。

## 四、播放地址

### `play_addr.url_list` 是加密的，不要碰

返回的是 800 位 hex，不是 URL：

```
461e1cc2360fba02dfd82ea4cce1d8eb1d10ec3f5c81ac10fd55dd3c26460729ff8ca...
```

**不要试图解密。** 用 `video.play_addr.uri` 走官方播放接口：

```
https://www.douyin.com/aweme/v1/play/?video_id={uri}&ratio=1080p&line=0
```

它会 302 到真实 CDN。这是网页端播放器自己走的路，不需要逆任何加密。

请求必须带 `Referer: https://www.douyin.com/`，否则 403。

### `misc_download_addrs` 的明文地址不可用

里面确实有明文 CDN URL，但实测 403（Lego Server）——那是下载场景，鉴权维度不同。

### 视频可能非常大

实测有一条 19 分钟的视频 **207 MB**。所以任何"整条预下载"的方案都不成立。

## 五、mpv IPC 的坑

### 坑：`set` 命令只认字符串

这是本次最花时间的一个问题——暂停按钮报 `invalid parameter`。

| 命令 | 结果 |
| --- | --- |
| `["set","pause",true]` | ❌ invalid parameter |
| `["set","pause","yes"]` | ✅ |
| `["set","volume",80]` | ❌ invalid parameter |
| `["set","volume","80"]` | ✅ |
| `["seek",5,"absolute"]` | ✅（seek 的 target 要数字） |

**规则：属性值一律传字符串，布尔用 `"yes"`/`"no"`，数字转字符串。**
`seek` 是命令参数不是属性值，仍然传数字。

复现：`dotnet run --project src/DouyinDesktop.PlayerProbe -- ipc`

### 其它约定

- 管道：`--input-ipc-server=\\.\pipe\{name}`，一行一个 JSON 对象
- 请求带 `request_id`，回复靠它对上；事件没有 id
- `end-file` 的 `reason` 要区分：`eof`（播完）、`error`（加载失败）、`stop`（我们自己切走）
- `eof-reached` 属性和 `end-file` 事件会**同时**来，不去重会连跳两条
- `--input-default-bindings=no` + `--input-vo-keyboard=no`，否则 mpv 抢键盘

## 六、预取方案：三种都试过

用户要的是"切换视频不要重新加载"。试了三条路：

| 方案 | 切换耗时 | 结论 |
| --- | --- | --- |
| 直连 CDN（loadfile replace） | 700–1400 ms | 基线 |
| mpv playlist + `prefetch-playlist=yes` | 1200 ms | **更慢**，放弃 |
| 整条预下载到本地 | 首帧快，但 207MB 的视频下不完 | 浪费带宽和磁盘，放弃 |
| **本地流代理 + 只预取开头 1MB** | **132 ms** | 采用 |

### 为什么 playlist 预读没用

mpv 的 prefetch 只预读头部元数据。网络流真正花时间的是 302 + CDN 首包，
它省不掉。实测比直连还慢 400ms。

### 本地流代理怎么工作

```
播放第 N 条时  → 后台对第 N+1 条发 Range: bytes=0-1048575，1MB 留在内存
切到第 N+1 条  → mpv 播 http://127.0.0.1:{port}/v/{id}?u={uri}
               → 代理先吐内存里的 1MB（0 延迟），再从 1MB 处向 CDN 续传
```

为什么 1MB 而不是 2MB：CDN 慢的时候（实测 200KB/s）2MB 要下十秒，
反而挤占当前视频的带宽。1MB 约等于 1080p 的 2–4 秒，够 mpv 出首帧并建立缓冲。

为什么用 `TcpListener` 手写 HTTP 而不是 `HttpListener`：后者绑定端口在非管理员
账户下需要预先注册 URL ACL，会让"双击就能跑"变得很麻烦。

复现：`dotnet run --project src/DouyinDesktop.PlayerProbe -- proxy`
