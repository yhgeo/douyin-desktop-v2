# 接口笔记

> 全部结论来自 2026-10-21 的实测，不是推测。
> 每条都标了怎么复现——接口会变，能复现才修得动。

---

## 一、整体链路

```
POST ttwid.bytedance.com          → 拿 ttwid（设备标识，不用登录）
本地生成 s_v_web_id                → 指纹 ID
GET  /aweme/v1/web/module/feed/   → 推荐列表（a_bogus 签名）
GET  /aweme/v1/play/?video_id=... → 302 到 CDN，返回 MP4 字节流
mpv --wid=<子窗口> 播放            → 解码出画面
```

复现：`dotnet run --project src/DouyinDesktop.Probe`

---

## 二、凭据

| 凭据 | 怎么来 | 说明 |
| --- | --- | --- |
| `ttwid` | POST `https://ttwid.bytedance.com/ttwid/union/register/`，从 `Set-Cookie` 里取 | 匿名注册，不需要登录。约 460ms |
| `s_v_web_id` | 本地生成，格式 `verify_{时间36进制}_{8位}_{4位}_4{3位}_{4位}_{12位}` | 纯随机，服务端不校验具体值 |
| `msToken` | **空着也能用** | 服务端会在响应头 `X-Ms-Token` 下发，捡到就存 |

**结论：不需要移植 368 行的 msToken 算法。** 原以为这是必需项，实测服务端根本不校验。

凭据落盘在程序目录的 `data\session.json`（跟着 exe 走，只读位置才退回 `%LOCALAPPDATA%`），
冷启动省掉注册往返。游客凭据超过 7 天会重新注册，避免长期用同一个设备号；
**登录态不按天数作废**，等 Cookie 自己失效。

## 三、推荐流

```
GET https://www.douyin.com/aweme/v1/web/module/feed/?{params}&a_bogus={sig}&verifyFp=...
```

### 坑 1：`aweme_list` 是空的

真实数据在 `cards[].aweme`，而且 **`aweme` 是 JSON 字符串，需要二次解析**。

直接抄 `DouYin_Spider` 的解析会拿到空列表。`cards` 里没有 `aweme` 字段的是广告位/提示位，跳过。

### 坑 2：参数顺序敏感

`a_bogus` 算的是原始 query 串。参数顺序一变签名就对不上，
所以 `DeviceProfile.FeedParams` 里的顺序是照抄网页端的，别"整理"。

### 坑 3：翻页去重靠 `presented_ids`

传已展示过的 id 逗号分隔，服务端会避开。实测新一批 10 条重复 0 条。
`refresh_index` 每次递增。

### 坑 4：推荐流里**没有图集**（2026-10-25 复测）

`module/feed` + `tab/feed` 合计 80 条，`aweme_type` 全是 `0`（视频），
`images` 字段一条都没有；用户实际保存的现场数据 16 条也是 0。

所以「只看图集」这个开关目前**拉不到东西**（代码留着，接口可能变回来）。
图集的可靠入口只有一个：`aweme/post`（作者主页）。

早期版本确实混入过图文，接口后来不返回这个字段了——别照旧结论写逻辑。

## 四、播放地址

### `play_addr.url_list` 是加密的，不要碰

返回的是 800 位 hex，不是 URL：

```
461e1cc2360fba02dfd82ea4cce1d8eb1d10ec3f5c81ac10fd55dd3c26460729ff8ca...
```

**不要试图解密。** 用 `video.play_addr.uri` 走官方播放接口：

```
https://www.douyin.com/aweme/v1/play/?video_id={uri}&ratio=1080p&line=0
```

它会 302 到真实 CDN。这是网页端播放器自己走的路，不需要逆任何加密。

请求必须带 `Referer: https://www.douyin.com/`，否则 403。

### `misc_download_addrs` 的明文地址不可用

里面确实有明文 CDN URL，但实测 403（Lego Server）——那是下载场景，鉴权维度不同。

### 视频可能非常大

实测有一条 19 分钟的视频 **207 MB**。所以任何"整条预下载"的方案都不成立。

## 五、mpv IPC 的坑

### 坑：`set` 命令只认字符串

这是本次最花时间的一个问题——暂停按钮报 `invalid parameter`。

| 命令 | 结果 |
| --- | --- |
| `["set","pause",true]` | ❌ invalid parameter |
| `["set","pause","yes"]` | ✅ |
| `["set","volume",80]` | ❌ invalid parameter |
| `["set","volume","80"]` | ✅ |
| `["seek",5,"absolute"]` | ✅（seek 的 target 要数字） |

**规则：属性值一律传字符串，布尔用 `"yes"`/`"no"`，数字转字符串。**
`seek` 是命令参数不是属性值，仍然传数字。

复现：`dotnet run --project src/DouyinDesktop.PlayerProbe -- ipc`

### 其它约定

- 管道：`--input-ipc-server=\\.\pipe\{name}`，一行一个 JSON 对象
- 请求带 `request_id`，回复靠它对上；事件没有 id
- `end-file` 的 `reason` 要区分：`eof`（播完）、`error`（加载失败）、`stop`（我们自己切走）
- `eof-reached` 属性和 `end-file` 事件会**同时**来，不去重会连跳两条
- `--input-default-bindings=no` + `--input-vo-keyboard=no`，否则 mpv 抢键盘

## 六、预取方案：三种都试过

用户要的是"切换视频不要重新加载"。试了三条路：

| 方案 | 切换耗时 | 结论 |
| --- | --- | --- |
| 直连 CDN（loadfile replace） | 700–1400 ms | 基线 |
| mpv playlist + `prefetch-playlist=yes` | 1200 ms | **更慢**，放弃 |
| 整条预下载到本地 | 首帧快，但 207MB 的视频下不完 | 浪费带宽和磁盘，放弃 |
| **本地流代理 + 只预取开头 1MB** | **132 ms** | 采用 |

### 为什么 playlist 预读没用

mpv 的 prefetch 只预读头部元数据。网络流真正花时间的是 302 + CDN 首包，
它省不掉。实测比直连还慢 400ms。

### 本地流代理怎么工作

```
播放第 N 条时  → 后台对第 N+1 条发 Range: bytes=0-1048575，1MB 留在内存
切到第 N+1 条  → mpv 播 http://127.0.0.1:{port}/v/{id}?u={uri}
               → 代理先吐内存里的 1MB（0 延迟），再从 1MB 处向 CDN 续传
```

为什么 1MB 而不是 2MB：CDN 慢的时候（实测 200KB/s）2MB 要下十秒，
反而挤占当前视频的带宽。1MB 约等于 1080p 的 2–4 秒，够 mpv 出首帧并建立缓冲。

为什么用 `TcpListener` 手写 HTTP 而不是 `HttpListener`：后者绑定端口在非管理员
账户下需要预先注册 URL ACL，会让"双击就能跑"变得很麻烦。

复现：`dotnet run --project src/DouyinDesktop.PlayerProbe -- proxy`

## 八、登录

**方案：WebView2 跑官方登录页，只负责抓 Cookie，不自己实现扫码协议。**

登录涉及验证码、风控、二次校验，是深坑；而官方页面本身最不容易被判异常。

流程：

```
L 键 → LoginWindow（WebView2）→ 打开 www.douyin.com
     → 抖音自己弹出二维码
     → 每秒查一次 Cookie，出现 sessionid 就认为登录成功
     → 把整包 Cookie 拼成 "a=1; b=2" 存进 session.json
     → 之后所有接口请求都带这个 Cookie
```

判据是 `sessionid`（或 `sessionid_ss`）且长度 > 10，游客态不会有。

### 坑 1：浏览器进程一启动就退出（exit 0x80000003）

现象：`ProcessFailed` → `BrowserProcessExited`，userDataFolder 里留下 crashpad dump，
`last_version` 文件是空的（说明还没写版本就崩了）。

解法：`AdditionalBrowserArguments = "--no-sandbox"`。
这是受限环境（容器/沙箱/安全软件）里最常见的解法。加 `--disable-gpu` 单独不管用。

### 坑 2：访问已崩溃的控件会抛异常

`Web.CoreWebView2` 在浏览器进程崩掉后，**getter 本身就会 throw**。
所以不能写成 `if (Web.CoreWebView2 is null) return;`——这个判断在 try 外面就会炸。
必须把属性访问整个放进 try 里。

### 坑 3：登录后 Cookie 要能覆盖游客凭据

`DouyinSession.CookieHeader` 的拼接顺序是 ttwid → s_v_web_id → 登录 Cookie，
后者覆盖前者。登录态下 `IsStale` 永远为 false（不按天数作废，等 Cookie 自己失效）。

## 九、作者主页与 webSign

### 为什么需要这个接口

**推荐流（module/feed）几乎不推图集。** 实测扫 48 条，`images` 字段一条都没有，全是视频。
图集只能从作者主页的作品列表拿：`/aweme/v1/web/aweme/post/`。

图集在响应里的标志是 `aweme_type = 68`（视频是 0），数据在 `images[]`。

比例不高——一个作者二十来条作品里通常 0–1 条图集，扫 6 个作者才碰到 2 条。

### 参数和推荐流不是一套

| 项 | 推荐流 | 作者主页 |
| --- | --- | --- |
| `version_code` | 170400 | **290100** |
| `version_name` | 17.4.0 | **29.1.0** |
| 特有字段 | `presented_ids`、`module_id` | `publish_video_strategy_type=2`、`from_user_page`、`support_dash`、`pc_libra_divert` |
| `verifyFp/fp` 位置 | a_bogus 之前 | **a_bogus 之后** |

照抄推荐流的参数会直接 403。

### webSign：这个接口额外要一个签名

`aweme/post` 在 secsdk 的 webSign 策略表里，除了 a_bogus 还要加
`x-secsdk-web-signature` + `timestamp`。

算法本身很简单：

```
MD5("{uifid}_{ts}_{盐}_{规范化query}&timestamp={ts}")  → 32 位小写 hex
盐 = A96D855A08C0A9707F8BEF0D9A527E4E（写死在 SDK 的 VM 常量池里）
```

麻烦在"规范化"：

- 保持原始参数顺序，**不排序**
- **value 要先解码，再用 `encodeURIComponent` 重编码**（空格→`%20`、`;`→`%3B`、`%7E`→`~`）
- key 只解码、不重编码
- 无等号的裸参数补成 `k=`
- query 里没有 `uifid` 时，从 UIFID cookie 取值追加到末尾
- 签名是对**规范化后的 query** 算的，所以必须发规范化后的 URL

实现见 `Core/Signing/WebSign.cs`。

### UIFID 从哪来

登录 Cookie 里通常只有 `UIFID_TEMP`，正式的 `UIFID` 是服务端在响应头
`Set-Cookie` 里下发的。第一次请求后抓下来存进 `session.json`，webSign 用它。

没有 UIFID 时签名是空 uifid 打头，服务端会拒。

### 推荐流混入图集（替代方案）

PC web 的两个推荐接口都不推图文：

| 接口 | 样本 | 图集 |
| --- | --- | --- |
| `module/feed` | 58 条 | 0 |
| `tab/feed` | 6 条（响应是 `aweme_list` 不是 `cards`） | 0 |

参数层面改不动（`module_id` 换成别的值服务端直接报 `status_code=4`）。
GitHub 上也没有能让推荐流返回图集的方案——现成项目（douyin-downloader 等）
都是"按作品 ID 取图集"，不涉及推荐流。

所以 App 里做了后台补充：加载推荐流后取前 2 个作者的 `sec_uid` 查主页，
把找到的图集插到当前条目后第 2 位。代价是每次加载多 2 个后台请求，不阻塞播放。
图集比例约 1/20，所以要刷几批才遇到一次。

## 十、窗口与输入法（WPF 相关，踩过才知道）

### 全屏不能改 WindowStyle

WPF 改 `WindowStyle` 会**重建窗口句柄**，HwndHost 跟着重建，mpv 还画在旧句柄上——
表现就是"按 F 黑屏一下然后重新加载"。

解法：窗口从头到尾 `WindowStyle="None"` + `WindowChrome` + 自绘标题栏。
全屏只是隐藏标题栏/侧栏、把窗口铺到整块屏幕（`Left/Top/Width/Height` + `Topmost`），
句柄不动，mpv 完全不重启。

### 输入法会抢单键

现象：开着中文输入法按 F，弹出候选框，全屏不生效。

`InputMethod.IsInputMethodEnabled="False"` **不够**——那只管 WPF 的输入焦点，
系统 IME 仍然会在窗口激活时抢按键。

解法：`ImmAssociateContext(hwnd, IntPtr.Zero)`，直接断掉窗口和输入法上下文的关联。
主窗口没有任何文本输入，禁用没有副作用。登录窗口故意不禁用（手机号登录要打字）。

### 测试脚本抢不到焦点会误导判断

`SetForegroundWindow` 在"调用者不是前台进程"时**静默失败**，返回 true 但没生效。
用 `AttachThreadInput` 借前台线程的输入队列才能真正抢到焦点（`tools/probe/keyshot.py` 已处理）。

排查"某个按键没反应"之前，先确认窗口真的是前台——否则会白改一通代码。

## 十一、2026-10-23/24 大排查：登录态、评论/主页、切视频

这一轮踩的坑最多，几乎每个都绕了远路。按"现象 → 根因 → 修法"记下来，
下次遇到类似症状可以直接对号入座。

### 11.1 总览：三个**互相独立**的问题，症状很像

| 现象 | 真正原因 | 修法 |
| --- | --- | --- |
| 评论/作者主页打不开（返回空 body） | 设备身份与 Cookie 不一致 | 重新登录；评论接口改用「浏览器 URL 模板」 |
| 视频疯狂跳、随后变大众内容 | 加载失败 + `end-file` 异步叠加，切换被连打 | 切换节流 + 时间戳限速 |
| 一快速切换就弹「登录已过期」 | 连切时请求太密被挡，误判为登录失效 | 连切后 3 秒内不做登录判断 |

**教训**：症状相似不代表同一个原因。一开始我把三个都归到"登录"上，
反复改参数、改 token，全部无效。

### 11.2 抖音对过期登录态的表现是**空 body**，不是错误码

- `status_code` 不会返回 8，也不会返回任何提示，就是 HTTP 200 + 长度 0
- 所以 `IsLoggedIn`（只判断有没有 Cookie）判断不出过期
- 登录健康检查只能靠"接口能不能读到数据"倒推

### 11.3 强校验接口（评论 / 作者作品）最稳的做法：照抄浏览器 URL

自己拼参数怎么调都差一点，最终方案：

```
抓一条浏览器真实发出的评论 URL → 存 data/api-templates.json
        ↓
每次只替换 aweme_id / cursor / count / msToken
        ↓
用我们自己的 ABogus 重新签名 → 发出去
```

实测：空响应 0 次，评论正常。

**为什么能行**：签名算法本身是对的（和参考实现逐字节一致），
Cookie 也是对的（重放浏览器 URL 能拿到 20428 字节），
差的只是**参数集合/取值**。照抄最省事。

⚠️ 这个方案**只适用于评论**。作者作品（`aweme/post`）不能用模板：
视频页根本不会发出该请求，模板抓不到，硬抓只会每次白等 8–14 秒。

### 11.4 webid 要分两个

| 文件 | 值 | 用途 |
| --- | --- | --- |
| `data/webid.txt` | 内置浏览器的真实 webid | 强校验接口（模板里已包含） |
| `data/webid-app.txt` | 本机随机生成、固定不变 | 推荐流 / 关注流 |

原因：强校验接口要求 webid 与登录设备一致；
而推荐个性化是按 webid 在服务端积累的，换一次就冷启动。
一个值满足不了两边。

### 11.5 登录为什么会"用一阵就掉"

我们保存的是**登录那一刻的 Cookie 快照**，抖音会在浏览器里不断刷新凭据。
不同步就会慢慢失效。

现有缓解：每 10 分钟从内置浏览器同步一次 Cookie
（只读 Cookie、不加载页面、1–2 秒、空闲时才做）。

### 11.6 诊断方法（这次真正有效的手段）

按有效性排序，下次优先用前两个：

1. **重放浏览器真实请求**
   用 `--webtest=<awemeId>` 抓一条浏览器 URL，用我们的 Cookie 重放。
   一步就能区分"是请求的问题"还是"账号/网络的问题"。
2. **和参考实现做对齐测试**
   固定时间戳 + 固定随机数，让 Python 参考实现和我们的 C# 各算一次签名，
   逐字节比对。`tmp/ab_ref.py`（本地临时脚本，`/tmp/` 不进版本库）+ `probe sign` 就是干这个的。
3. **逐个参数替换**
   在浏览器 URL 上每次只替换一个参数值再重签，看哪个值会让请求失效
   —— 就是这样定位到 webid 的。

### 11.7 代码里哪些是"补丁"，为什么留着

| 位置 | 作用 | 备注 |
| --- | --- | --- |
| `App/ApiTemplate.cs` | 浏览器 URL 模板存取 | 强校验接口的核心依赖 |
| `App/TemplateFetcher.cs` | 后台抓模板（屏幕外 WebView2） | 失败后冷却 5 分钟 |
| `App/WebCookieSync.cs` | 只读浏览器 Cookie | 登录续期、免扫码恢复 |

| `App/LoginHealth.cs` | 登录健康状态 | 设置页 + 右下角徽章读它 |
| `App/WebTestWindow.cs` | `--webtest` 调试模式 | 不参与正常流程，排障用 |

### 11.8 不要重犯的坑

- **同一个时间戳字段不能混用 `DateTime.Now` 和 `DateTime.UtcNow`**
  混用会算出负数，节流逻辑变成"永远拦截"，表现是按键全失效。
- **不要用布尔锁做异步流程的重入保护**
  异常/挂起时锁不释放，功能直接死掉。用时间戳限速。
- **mpv 是 HwndHost，会盖住同区域的 WPF 内容**
  进度条、图集都踩过；这类元素必须放在 mpv 区域外面。
- **探针（Probe）有自己的数据目录**
  `src/DouyinDesktop.Probe/bin/Debug/net10.0/data`，
  复制会话/模板要放对位置，否则测的完全是另一份数据。
- **`probe` 里 `Session` 为 null 时赋值会静默跳过**
  要改会话字段，先 `await EnsureSessionAsync()`。
- **改动了 webid / ttwid / s_v_web_id 的版本，必须提醒用户重新登录一次**
  否则设备身份与 Cookie 对不上，服务端当游客处理。
