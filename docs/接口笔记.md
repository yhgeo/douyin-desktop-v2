# 接口笔记

> 全部结论来自 2026-10-21 的实测，不是推测。
> 每条都标了怎么复现——接口会变，能复现才修得动。

---

## 一、整体链路

```
POST ttwid.bytedance.com          → 拿 ttwid（设备标识，不用登录）
本地生成 s_v_web_id                → 指纹 ID
GET  /aweme/v1/web/module/feed/   → 推荐列表（a_bogus 签名）
GET  /aweme/v1/play/?video_id=... → 302 到 CDN，返回 MP4 字节流
mpv --wid=<子窗口> 播放            → 解码出画面
```

复现：`dotnet run --project src/DouyinDesktop.Probe`

---

## 二、凭据

| 凭据 | 怎么来 | 说明 |
| --- | --- | --- |
| `ttwid` | POST `https://ttwid.bytedance.com/ttwid/union/register/`，从 `Set-Cookie` 里取 | 匿名注册，不需要登录。约 460ms |
| `s_v_web_id` | 本地生成，格式 `verify_{时间36进制}_{8位}_{4位}_4{3位}_{4位}_{12位}` | 纯随机，服务端不校验具体值 |
| `msToken` | **空着也能用** | 服务端会在响应头 `X-Ms-Token` 下发，捡到就存 |

**结论：不需要移植 368 行的 msToken 算法。** 原以为这是必需项，实测服务端根本不校验。

凭据落盘在程序目录的 `data\session.json`（跟着 exe 走，只读位置才退回 `%LOCALAPPDATA%`），
冷启动省掉注册往返。游客凭据超过 7 天会重新注册，避免长期用同一个设备号；
**登录态不按天数作废**，等 Cookie 自己失效。

## 三、推荐流

```
GET https://www.douyin.com/aweme/v1/web/module/feed/?{params}&a_bogus={sig}&verifyFp=...
```

### 坑 1：`aweme_list` 是空的

真实数据在 `cards[].aweme`，而且 **`aweme` 是 JSON 字符串，需要二次解析**。

直接抄 `DouYin_Spider` 的解析会拿到空列表。`cards` 里没有 `aweme` 字段的是广告位/提示位，跳过。

### 坑 2：参数顺序敏感

`a_bogus` 算的是原始 query 串。参数顺序一变签名就对不上，
所以 `DeviceProfile.FeedParams` 里的顺序是照抄网页端的，别"整理"。

### 坑 3：翻页去重靠 `presented_ids`

传已展示过的 id 逗号分隔，服务端会避开。实测新一批 10 条重复 0 条。
`refresh_index` 每次递增。

### 坑 4：推荐流里**没有图集**（2026-10-25 复测）

`module/feed` + `tab/feed` 合计 80 条，`aweme_type` 全是 `0`（视频），
`images` 字段一条都没有；用户实际保存的现场数据 16 条也是 0。

所以「只看图集」这个开关**拉不到东西**，2026-10-26 已从界面和代码里删掉
（`FetchImagesOnlyAsync` 一并删除；老配置里的 `ImageOnly` 字段现在被直接忽略，
否则 UI 上关不掉会让用户一直卡在"没找到图集"）。
图集的可靠入口只有一个：`aweme/post`（作者主页）。

早期版本确实混入过图文，接口后来不返回这个字段了——别照旧结论写逻辑。

## 四、播放地址

### `play_addr.url_list` 是加密的，不要碰

返回的是 800 位 hex，不是 URL：

```
461e1cc2360fba02dfd82ea4cce1d8eb1d10ec3f5c81ac10fd55dd3c26460729ff8ca...
```

**不要试图解密。** 用 `video.play_addr.uri` 走官方播放接口：

```
https://www.douyin.com/aweme/v1/play/?video_id={uri}&ratio=1080p&line=0
```

它会 302 到真实 CDN。这是网页端播放器自己走的路，不需要逆任何加密。

请求必须带 `Referer: https://www.douyin.com/`，否则 403。

### `misc_download_addrs` 的明文地址不可用

里面确实有明文 CDN URL，但实测 403（Lego Server）——那是下载场景，鉴权维度不同。

### 视频可能非常大

实测有一条 19 分钟的视频 **207 MB**。所以任何"整条预下载"的方案都不成立。

## 五、mpv IPC 的坑

### 坑：`set` 命令只认字符串

这是本次最花时间的一个问题——暂停按钮报 `invalid parameter`。

| 命令 | 结果 |
| --- | --- |
| `["set","pause",true]` | ❌ invalid parameter |
| `["set","pause","yes"]` | ✅ |
| `["set","volume",80]` | ❌ invalid parameter |
| `["set","volume","80"]` | ✅ |
| `["seek",5,"absolute"]` | ✅（seek 的 target 要数字） |

**规则：属性值一律传字符串，布尔用 `"yes"`/`"no"`，数字转字符串。**
`seek` 是命令参数不是属性值，仍然传数字。

复现：`dotnet run --project src/DouyinDesktop.PlayerProbe -- ipc`

### 其它约定

- 管道：`--input-ipc-server=\\.\pipe\{name}`，一行一个 JSON 对象
- 请求带 `request_id`，回复靠它对上；事件没有 id
- `end-file` 的 `reason` 要区分：`eof`（播完）、`error`（加载失败）、`stop`（我们自己切走）
- `eof-reached` 属性和 `end-file` 事件会**同时**来，不去重会连跳两条
- `--input-default-bindings=no` + `--input-vo-keyboard=no`，否则 mpv 抢键盘

## 六、预取方案：三种都试过

用户要的是"切换视频不要重新加载"。试了三条路：

| 方案 | 切换耗时 | 结论 |
| --- | --- | --- |
| 直连 CDN（loadfile replace） | 700–1400 ms | 基线 |
| mpv playlist + `prefetch-playlist=yes` | 1200 ms | **更慢**，放弃 |
| 整条预下载到本地 | 首帧快，但 207MB 的视频下不完 | 浪费带宽和磁盘，放弃 |
| **本地流代理 + 只预取开头 1MB** | **132 ms** | 采用 |

### 为什么 playlist 预读没用

mpv 的 prefetch 只预读头部元数据。网络流真正花时间的是 302 + CDN 首包，
它省不掉。实测比直连还慢 400ms。

### 本地流代理怎么工作

```
播放第 N 条时  → 后台对第 N+1 条发 Range: bytes=0-1048575，1MB 留在内存
切到第 N+1 条  → mpv 播 http://127.0.0.1:{port}/v/{id}?u={uri}
               → 代理先吐内存里的 1MB（0 延迟），再从 1MB 处向 CDN 续传
```

为什么 1MB 而不是 2MB：CDN 慢的时候（实测 200KB/s）2MB 要下十秒，
反而挤占当前视频的带宽。1MB 约等于 1080p 的 2–4 秒，够 mpv 出首帧并建立缓冲。

为什么用 `TcpListener` 手写 HTTP 而不是 `HttpListener`：后者绑定端口在非管理员
账户下需要预先注册 URL ACL，会让"双击就能跑"变得很麻烦。

复现：`dotnet run --project src/DouyinDesktop.PlayerProbe -- proxy`

## 八、登录

**方案：WebView2 跑官方登录页，只负责抓 Cookie，不自己实现扫码协议。**

登录涉及验证码、风控、二次校验，是深坑；而官方页面本身最不容易被判异常。

流程：

```
L 键 → LoginWindow（WebView2）→ 打开 www.douyin.com
     → 抖音自己弹出二维码
     → 每秒查一次 Cookie，出现 sessionid 就认为登录成功
     → 把整包 Cookie 拼成 "a=1; b=2" 存进 session.json
     → 之后所有接口请求都带这个 Cookie
```

判据是 `sessionid`（或 `sessionid_ss`）且长度 > 10，游客态不会有。

### 坑 1：浏览器进程一启动就退出（exit 0x80000003）

现象：`ProcessFailed` → `BrowserProcessExited`，userDataFolder 里留下 crashpad dump，
`last_version` 文件是空的（说明还没写版本就崩了）。

解法：`AdditionalBrowserArguments = "--no-sandbox"`。
这是受限环境（容器/沙箱/安全软件）里最常见的解法。加 `--disable-gpu` 单独不管用。

### 坑 2：访问已崩溃的控件会抛异常

`Web.CoreWebView2` 在浏览器进程崩掉后，**getter 本身就会 throw**。
所以不能写成 `if (Web.CoreWebView2 is null) return;`——这个判断在 try 外面就会炸。
必须把属性访问整个放进 try 里。

### 坑 3：登录后 Cookie 要能覆盖游客凭据

`DouyinSession.CookieHeader` 的拼接顺序是 ttwid → s_v_web_id → 登录 Cookie，
后者覆盖前者。登录态下 `IsStale` 永远为 false（不按天数作废，等 Cookie 自己失效）。

## 九、作者主页与 webSign

### 为什么需要这个接口

**推荐流（module/feed）几乎不推图集。** 实测扫 48 条，`images` 字段一条都没有，全是视频。
图集只能从作者主页的作品列表拿：`/aweme/v1/web/aweme/post/`。

图集在响应里的标志是 `aweme_type = 68`（视频是 0），数据在 `images[]`。

比例不高——一个作者二十来条作品里通常 0–1 条图集，扫 6 个作者才碰到 2 条。

### 参数和推荐流不是一套

| 项 | 推荐流 | 作者主页 |
| --- | --- | --- |
| `version_code` | 170400 | **290100** |
| `version_name` | 17.4.0 | **29.1.0** |
| 特有字段 | `presented_ids`、`module_id` | `publish_video_strategy_type=2`、`from_user_page`、`support_dash`、`pc_libra_divert` |
| `verifyFp/fp` 位置 | a_bogus 之前 | **a_bogus 之后** |

照抄推荐流的参数会直接 403。

### webSign：这个接口额外要一个签名

`aweme/post` 在 secsdk 的 webSign 策略表里，除了 a_bogus 还要加
`x-secsdk-web-signature` + `timestamp`。

算法本身很简单：

```
MD5("{uifid}_{ts}_{盐}_{规范化query}&timestamp={ts}")  → 32 位小写 hex
盐 = A96D855A08C0A9707F8BEF0D9A527E4E（写死在 SDK 的 VM 常量池里）
```

麻烦在"规范化"：

- 保持原始参数顺序，**不排序**
- **value 要先解码，再用 `encodeURIComponent` 重编码**（空格→`%20`、`;`→`%3B`、`%7E`→`~`）
- key 只解码、不重编码
- 无等号的裸参数补成 `k=`
- query 里没有 `uifid` 时，从 UIFID cookie 取值追加到末尾
- 签名是对**规范化后的 query** 算的，所以必须发规范化后的 URL

实现见 `Core/Signing/WebSign.cs`。

### UIFID 从哪来

登录 Cookie 里通常只有 `UIFID_TEMP`，正式的 `UIFID` 是服务端在响应头
`Set-Cookie` 里下发的。第一次请求后抓下来存进 `session.json`，webSign 用它。

没有 UIFID 时签名是空 uifid 打头，服务端会拒。

### 推荐流混入图集（替代方案）

PC web 的两个推荐接口都不推图文：

| 接口 | 样本 | 图集 |
| --- | --- | --- |
| `module/feed` | 58 条 | 0 |
| `tab/feed` | 6 条（响应是 `aweme_list` 不是 `cards`） | 0 |

参数层面改不动（`module_id` 换成别的值服务端直接报 `status_code=4`）。
GitHub 上也没有能让推荐流返回图集的方案——现成项目（douyin-downloader 等）

图集比例约 1/20，所以要刷几批才遇到一次。

## 十、窗口与输入法（WPF 相关，踩过才知道）

### 全屏不能改 WindowStyle

WPF 改 `WindowStyle` 会**重建窗口句柄**，HwndHost 跟着重建，mpv 还画在旧句柄上——
表现就是"按 F 黑屏一下然后重新加载"。

解法：窗口从头到尾 `WindowStyle="None"` + `WindowChrome` + 自绘标题栏。
全屏只是隐藏标题栏/侧栏、把窗口铺到整块屏幕（`Left/Top/Width/Height` + `Topmost`），
句柄不动，mpv 完全不重启。

### 输入法会抢单键

现象：开着中文输入法按 F，弹出候选框，全屏不生效。

`InputMethod.IsInputMethodEnabled="False"` **不够**——那只管 WPF 的输入焦点，
系统 IME 仍然会在窗口激活时抢按键。

解法：`ImmAssociateContext(hwnd, IntPtr.Zero)`，直接断掉窗口和输入法上下文的关联。
主窗口没有任何文本输入，禁用没有副作用。登录窗口故意不禁用（手机号登录要打字）。

### 测试脚本抢不到焦点会误导判断

`SetForegroundWindow` 在"调用者不是前台进程"时**静默失败**，返回 true 但没生效。
用 `AttachThreadInput` 借前台线程的输入队列才能真正抢到焦点（`tools/probe/keyshot.py` 已处理）。

排查"某个按键没反应"之前，先确认窗口真的是前台——否则会白改一通代码。

## 十一、2026-10-23/24 大排查：登录态、评论/主页、切视频

这一轮踩的坑最多，几乎每个都绕了远路。按"现象 → 根因 → 修法"记下来，
下次遇到类似症状可以直接对号入座。

### 11.1 总览：三个**互相独立**的问题，症状很像

| 现象 | 真正原因 | 修法 |
| --- | --- | --- |
| 评论/作者主页打不开（返回空 body） | 设备身份与 Cookie 不一致 | 重新登录；评论接口改用「浏览器 URL 模板」 |
| 视频疯狂跳、随后变大众内容 | 加载失败 + `end-file` 异步叠加，切换被连打 | 切换节流 + 时间戳限速 |
| 一快速切换就弹「登录已过期」 | 连切时请求太密被挡，误判为登录失效 | 连切后 3 秒内不做登录判断 |

**教训**：症状相似不代表同一个原因。一开始我把三个都归到"登录"上，
反复改参数、改 token，全部无效。

### 11.2 抖音对过期登录态的表现是**空 body**，不是错误码

- `status_code` 不会返回 8，也不会返回任何提示，就是 HTTP 200 + 长度 0
- 所以 `IsLoggedIn`（只判断有没有 Cookie）判断不出过期
- 登录健康检查只能靠"接口能不能读到数据"倒推

### 11.3 强校验接口（评论 / 作者作品）最稳的做法：照抄浏览器 URL

自己拼参数怎么调都差一点，最终方案：

```
抓一条浏览器真实发出的评论 URL → 存 data/api-templates.json
        ↓
每次只替换 aweme_id / cursor / count / msToken
        ↓
用我们自己的 ABogus 重新签名 → 发出去
```

实测：空响应 0 次，评论正常。

**为什么能行**：签名算法本身是对的（和参考实现逐字节一致），
Cookie 也是对的（重放浏览器 URL 能拿到 20428 字节），
差的只是**参数集合/取值**。照抄最省事。

⚠️ 这个方案**只适用于评论**。作者作品（`aweme/post`）不能用模板：
视频页根本不会发出该请求，模板抓不到，硬抓只会每次白等 8–14 秒。

作者作品走"自己拼参数 + webSign"，**但 webid 必须是浏览器真实值**（见 11.4）。
用随机 webid 时服务端返回 HTTP 200 + 空 body，看起来和登录过期一模一样。

### 11.4 webid：登录态下**统一用浏览器真实值**（2026-10-25 修正）

| 文件 | 值 | 什么时候用 |
| --- | --- | --- |
| `data/webid.txt` | 内置浏览器的真实 webid | **登录后所有接口都用它** |
| `data/webid-app.txt` | 本机随机生成、固定不变 | 只有游客态兜底 |

**旧结论（"两个 webid 分工，推荐流用随机值"）是错的**，已推翻：

- 作者作品 `aweme/post` 用随机 webid → HTTP 200 但 **body 长度 0**（不是 403、不是报错，
  就是静默空）。换成 `webid.txt` 后同一批作者立刻返回 20–23 条作品。
- 也就是说，**空 body 不一定是登录过期**，也可能是 webid 与 Cookie 对不上。
  这个坑和"登录态失效"的症状一模一样，非常容易误判。
- 推荐流用哪个 webid 都能返回内容（两批作者完全不同，主题相近，无法证明哪个更个性化），
  但**同一份 Cookie 配两个不同 webid 本身就是设备身份不一致**。
  所以登录态下统一用浏览器值，只在没有 `webid.txt`（游客/没登录过）时才退回随机值。

代码：`DeviceProfile.EffectiveWebId` 统一出口，`DouyinClient` 里所有接口都用它。

### 11.4.1 推荐流之前漏了 `uifid`

浏览器**每个**接口都带 `uifid`（secsdk 设备指纹），评论和主页都有，
但推荐流的参数表里一直没加。少了它，服务端只能按"设备"推，拿不到账号级个性化。
2026-10-25 补上（`FeedParams` 的可选参数）。

### 11.5 登录为什么会"用一阵就掉"

我们保存的是**登录那一刻的 Cookie 快照**，抖音会在浏览器里不断刷新凭据。
不同步就会慢慢失效。

现有缓解：每 10 分钟从内置浏览器同步一次 Cookie
（只读 Cookie、不加载页面、1–2 秒、空闲时才做）。

### 11.6 诊断方法（这次真正有效的手段）

按有效性排序，下次优先用前两个：

1. **重放浏览器真实请求**
   用 `--webtest=<awemeId>` 抓一条浏览器 URL，用我们的 Cookie 重放。
   一步就能区分"是请求的问题"还是"账号/网络的问题"。
2. **和参考实现做对齐测试**
   固定时间戳 + 固定随机数，让 Python 参考实现和我们的 C# 各算一次签名，
   逐字节比对。`tmp/ab_ref.py`（本地临时脚本，`/tmp/` 不进版本库）+ `probe sign` 就是干这个的。
3. **逐个参数替换**
   在浏览器 URL 上每次只替换一个参数值再重签，看哪个值会让请求失效
   —— 就是这样定位到 webid 的。

### 11.7 代码里哪些是"补丁"，为什么留着

| 位置 | 作用 | 备注 |

| `App/ApiTemplate.cs` | 浏览器 URL 模板存取 | 强校验接口的核心依赖 |
| `App/TemplateFetcher.cs` | 后台抓模板（屏幕外 WebView2） | 失败后冷却 5 分钟 |

| `Core/SessionExpiry.cs` | 从 `sid_guard` 算到期时间 | 纯逻辑，有单元测试；竖线是 `%7C` |
| `App/LoginHealth.cs` | 登录健康状态 | 设置页 + 右下角徽章读它 |
| `App/WebTestWindow.cs` | `--webtest` 调试模式 | 不参与正常流程，排障用 |

### 11.8 不要重犯的坑

- **同一个时间戳字段不能混用 `DateTime.Now` 和 `DateTime.UtcNow`**
  混用会算出负数，节流逻辑变成"永远拦截"，表现是按键全失效。
- **不要用布尔锁做异步流程的重入保护**
  异常/挂起时锁不释放，功能直接死掉。用时间戳限速。
- **mpv 是 HwndHost，会盖住同区域的 WPF 内容**
  进度条、图集都踩过；这类元素必须放在 mpv 区域外面。
- **探针（Probe）有自己的数据目录**
  `src/DouyinDesktop.Probe/bin/Debug/net10.0/data`，
  复制会话/模板要放对位置，否则测的完全是另一份数据。
- **`probe` 里 `Session` 为 null 时赋值会静默跳过**
  要改会话字段，先 `await EnsureSessionAsync()`。
- **改动了 webid / ttwid / s_v_web_id 的版本，必须提醒用户重新登录一次**
  否则设备身份与 Cookie 对不上，服务端当游客处理。

## 十二、性能：启动与切换的实测（2026-10-25）

数据来自 `data/logs/app-*.log`，不是估算。

### 12.1 切换视频：446 次样本

| 指标 | 值 |
| --- | --- |
| 最小 | 18ms |
| 中位 | 197ms |
| 平均 | 309ms |
| 最大 | 2844ms |
| 命中预取（<150ms） | 42% |

命中率偏低的原因不是预取逻辑，而是**带宽被抢**：切视频瞬间弹幕会连发
3 个请求（0–32s / 32–64s / 64–96s），和视频首包抢同一条连接。

修法：弹幕要等 `file-loaded` 之后才开始拉（`_fileLoadedFor` 标记）。
原来只判断 `time-pos > 0.05`，但切换瞬间这个值还是上一条的，条件立刻成立。

### 12.2 启动：探活白等 450–590ms

原来"接着上次看"会先发一个 1KB Range 请求确认播放地址没过期（实测 449ms / 590ms），
**每次启动都白等**。而地址真失效时 `OnFileFailed` 本来就会刷新地址重试、
整批失效就重新拉推荐——探活是重复保险。

现在：直接播；超过 6 小时的现场直接拉新推荐（地址肯定过期了）。

### 12.3 当前播放的这条从来不进缓存

`PrefetchCache` 只由 `PrefetchAsync`（预取下一条）写入，正在播的那条走
`PassthroughAsync` 直接转发，**开头 1MB 不落盘**。所以"接着上次看"那条
必然重新走网络，实测 `file-loaded` 1.08 秒。

修法：`PassthroughAsync` 在 `start == 0` 时边转发边攒前 1MB，然后落盘。

## 十三、点赞能不能跟官方同步（2026-10-25 探明）

结论先给：**读方向完全可行，写方向在当前 HTTP 栈下不可行。**

### 13.1 读：服务端本来就给权威状态

`user_digged`（1=点过，0=没点）在**推荐流和详情接口里都有**：

```
推荐流 10 条 → 10/10 条带 user_digged，值与详情接口完全一致
```

所以客户端不需要额外请求、也不需要本地猜。代码已经改成：
`ShowInfo` 里 `user_digged` 非空就**双向**同步本地状态（以前只加不删，
在网页版取消过的赞这里会一直显示"已赞"）。

`digg_count` 里已经含了自己那一票，所以"已赞"时**不要**再 +1（以前会多算一个）。

### 13.2 写：`status_code=0` 是假的

点赞请求返回 `status_code=0`，但连采样 4.5 秒，`user_digged` 一直是 0、
`digg_count` 一个都不动。

逐个排除了三种猜测：

| 猜测 | 做法 | 结果 |
| --- | --- | --- |
| 缺 CSRF | 补 `x-secsdk-csrf-token`（Cookie 的 passport_csrf_token） | 无效 |
| 缺 secsdk 设备头 | 抓浏览器真实头，发现浏览器**只发** `x-secsdk-csrf-token: DOWNGRADE`，根本没有 `x-tt-session-dtrait` | 无效 |
| CSRF 值不对 | 换成浏览器真实值 `DOWNGRADE` | 无效 |

补 `x-tt-token`（取 Cookie 的 `x_tt_token`）也试过，无效。

### 13.3 最可能的原因

**读接口全部正常、写接口全部静默丢弃**，这个组合指向 **TLS 指纹**：
.NET 的 HttpClient 走 SChannel，和 Chrome 的 TLS 握手特征不同。
抖音对读接口宽容、对写接口严格，很符合"防刷赞"的风控取向。

要绕过只能换 HTTP 栈（BoringSSL / curl_cffi 那套），成本高、且是在主动对抗风控，
暂时不做。

### 13.4 现在的产品处理

- 点赞失败时**如实告诉用户**"接口被风控挡了，按 B 在浏览器里点"，不假装成功
- `按 B` 打开网页版是 0 维护成本的替代路径
- 保留 `--capture-headers` 诊断模式和 `probe diggsync` 回归验证，
  将来换 HTTP 栈时能立刻验证

### 13.5 顺带修的一个显示 bug

`digg_count` 在服务端已经含了自己，界面又 +1，导致"已赞"状态下的数字偏大。
现在只在"本地刚点、服务端还没反映"时才 +1。

## 十四、关注流"变成大众视频"的真相（2026-10-25）

用户反馈：切到关注页，看到的像大众推荐。查下来**接口完全正常**，
问题在"关注流是什么"这件事本身。

### 14.1 ⚠️ `follow_status` 不能用来判断真实关注关系

`follow/feed` 结构是 `{cursor, data:[{aweme:{...}}]}`，
响应里每条都带 `author.follow_status = 1`，看起来"全部已关注"。

**但这是假的。** 两个决定性的反证：

1. **换 webid，作者完全不同，但都标着 1**
   - `webid-app`（7699892562177689122）→ 瑞虎剧场、心心漫漫说、结巴说书…
   - `webid.txt`（7699918173528173529130536）→ 谭指一辉间soso、阿诺探影、晓鱼说电影…
   两组都是"已关注 100%"，但作者完全不重叠。
2. **游客态也能拉到 11 条**
   把内存里的 `LoginCookies` 清空（纯游客）再请求 `follow/feed`，
   照样返回 11 条（紫霞剧场、心动短剧场…）。

结论：这个字段是服务端给"关注流条目"打的标记，**不代表真实关注关系**；
而且 `follow/feed` 对游客也会填充内容。**别再用它做判断。**

三组参数（`pull_type=2` / `0` / 只留 count+refresh_index）结果一致，
`refresh_index` 从 0 试到 12 也不影响内容——所以也不是参数问题。

### 14.1.1 真正的问题是"设备与账号不匹配"

同一份 Cookie 下：

| 接口 | 结果 |
| --- | --- |
| 评论（走浏览器模板 URL） | 正常，20 条 |
| 作者主页（浏览器 webid） | 正常，20–23 条 |
| `follow/feed` | 返回填充内容（不是真实关注列表） |
| `user/profile/self` | `status_code=8 用户未登录` |

`profile/self` 说未登录、写接口（点赞）静默失败、关注流给填充内容，
但读接口又都能用 —— 这是**登录态与设备标识不匹配**的典型症状：
服务端认得 sessionid，但不认这个"设备"，于是降级处理。

**诱因**：2026-10-25 把推荐流/关注流的 webid 从 `webid-app.txt`（本机随机值）
改成了 `webid.txt`（浏览器真实值）。设备身份变了，但没重新登录。

**处理**：改 webid / ttwid / s_v_web_id 之后**必须重新登录一次**，
让服务端把新设备与账号重新绑定。这条在 `MEMORY.md` 里早就写着，这次没照做。

### 14.2 真正的原因：它是"作品流"，不是"每人一条"

关注流**按发布时间倒序**。短剧/漫剧号一天发几十条，于是：

```
一页 11 条里：追个剧文化 ×2、西溪棉花糖剧场 ×2、美光-恋爱剧场 ×4 …
```

11 条只来自 3–4 个作者，标题又都是"高分热剧推荐""看了第一集想看第二集"，
整页看起来就跟推荐流没区别——但确实是关注的人发的。

**处理**：拉回来后按 `author.sec_uid` 去重，只留每个作者最新一条。
一页里能看到更多人，翻页时还会遇到同作者的新内容（跨页不去重）。

### 14.3 附带发现：`profile/self` 拿不到自己的信息

```
GET /aweme/v1/web/user/profile/self/  →  status_code=8「用户未登录」
GET /aweme/v1/web/im/user/info/       →  "url doesn't match"
```

但关注流、评论、作者主页在同一份 Cookie 下全部正常，
说明这个接口另有门槛（可能是 webSign 或别的策略表），**不影响正常功能**。
想拿自己的 uid/sec_uid 目前没有可靠办法，别在这上面浪费时间。

### 14.4 设备漂移的第二个表现：评论全空

评论走"浏览器模板 URL"。模板是**抓取那一刻**的设备环境，
里面存着当时的 `webid` / `uifid` / `verifyFp`。

重新登录后设备标识换了，但 `BuildFromTemplate` 只替换
`aweme_id` / `cursor` / `count` / `msToken` —— **新 Cookie 配旧设备**，
服务端返回 HTTP 200 + 空 body（还是那个不报错的套路）。

```
[评论URL] ...&webid=7699918173529130536&...     ← 旧设备
当前 data/webid.txt = 7700307701904999946        ← 新设备
→ 评论 0 条，原始返回：（空）
```

**同一个根因，不同接口的容错程度不一样**：

| 接口 | 参数来源 | 受影响？ |
| --- | --- | --- |
| 作者主页 | 自己拼 | 否（强校验但参数自己生成，用的是当前 webid） |
| 评论 | 浏览器模板 | **是，全空** |
| 关注流 | 自己拼 | 是，返回填充内容 |
| 点赞 | 自己拼 | 是，静默失败 |

修法：`BuildFromTemplate` 里把 `webid` / `uifid` / `verifyFp` / `fp`
也按当前设备替换掉。验证后评论从 0 条恢复到 20 条。

**教训**：模板复用的前提是"设备环境不变"。任何设备标识的替换点都要一起检查，
漏一个就是整条链路静默失败。

## 十六、搜索接口：已打通（2026-10-27，推翻 10-25 的"做不了"）

### 16.1 现在的做法

`SearchRawAsync2` → `SearchAsync`，实测 `status_code=0`，一页 16 条。

抓包对照（`data/search-capture.json`，浏览器真实请求）后确认的关键点：

- 签名用 **`a_bogus`**（`_signer.SignQuery`），**不是** `x_bogus`——后者早就废弃了
- 参数要齐：`enable_history` / `disable_rs` / `need_filter_settings` / `list_type` /
  `pc_search_top_1_params`，少一个都可能是 2483
- `webid` 用**与 Cookie 配套**的那个（登录态下就是 `webid.txt` 里的值）
- 请求头只要 7 个普通的，**没有任何 secsdk 特殊头**（`x-tt-token` 之类根本不存在）
- 响应数据在 **`data[].aweme_info`**，而 `aweme_list` 是 **null**；
  `data` 里还混着用户卡片、直播、话题，只取带 `aweme_info` 的节点

### 16.2 之前为什么一直 2483

10-25 那次结论是"校验客户端环境（TLS 指纹 / bd-ticket-guard）"，**这个结论是错的**。

真正的原因是当时**设备标识与 Cookie 不配套**（就是"设备漂移"）：
那阵子 webid 策略还在反复改，`webid.txt` 和 session 里的 Cookie 不是同一套设备。
浏览器（WebView2，带完整设备指纹 + 登录态）能搜，纯 HTTP 客户端不能，
看起来就像"必须真实浏览器环境"。

10-26 统一 webid、10-27 用注入 Cookie 的 WebView2 抓包对照后，
同样的纯 HTTP 请求直接通了——**没有换 HTTP 栈，也没有伪造 TLS**。

### 16.3 教训

**"某个接口做不了"这种结论，在设备身份没对齐之前不要下。**

判断顺序应该是：先 `user/profile/self` 回 0（真登录）→ 再看 `webid.txt`
与 Cookie 是否同一套设备 → 最后才怀疑接口本身。
反过来做会得出"要 TLS 指纹"这种既费钱又劝退的结论。

## 十七、喜欢 / 收藏 / 登录态（2026-10-26 实测）

这一轮把"能不能拉自己喜欢和收藏"探到了底，同时挖出一个**影响所有浏览器抓取**的根因。

### 17.1 喜欢接口存在，但缺一样东西：自己的 sec_user_id

`GET /aweme/v1/web/aweme/favorite/`

| 请求方式 | 结果 |
| --- | --- |
| 不带 webSign | `403 Blocked by ArgusSecurityPlugin Signature Not Found` |
| 带 webSign、只给 count+cursor | `200 {"aweme_list":null}` |
| 带 webSign + 空 sec_user_id | `200 {"aweme_list":null}` |
| 带 webSign + **别人的** sec_user_id | `200 {"status_code":0,"sec_uid":"…","aweme_list":null}` |
| 带 webSign + `user_id=自己的数字 uid` | `200 {"sec_uid":"","uid":"…","aweme_list":null}` |

**结论**：签名这关能过（webSign 有效），接口也认 `sec_user_id` 这个参数（会回显），
但服务端**必须拿到一个真实的 sec_user_id 才会去查列表**。
空值、或者只有数字 uid，都直接给 `aweme_list: null`——不报错，就是空。

所以喜欢/收藏的**读方向是通的**，卡点不在接口，在"拿不到自己的 sec_user_id"。

### 17.2 为什么拿不到自己的 sec_user_id（**已解决：登录有效就能拿到**）

> **2026-10-26 01:10 更正**：下面这些失败全部发生在**登录态已失效**的情况下。
> 重新扫码登录后，`user/profile/self` 直接返回完整用户对象，
> `user.sec_uid` 就在里面（实测 `MS4wLjABAAAAD82zLM-kaeFmTfiOGNDVhOHGmCzP10iDtGQ23yYhArs`，
> 昵称 Tea、uid 101518012740）。
>
> **所以拿 sec_uid 不需要 WebView2、不需要反爬绕过——登录有效就行。**
> 之前误以为是"接口另有门槛"，其实是把"登录失效"读成了"接口限制"。

失效状态下试过的全部路子（留作反面记录）：

| 路径 | 结果 |
| --- | --- |
| `/aweme/v1/web/user/profile/self/` | `status_code=8 用户未登录`（加 webSign 也一样） |
| `/aweme/v1/web/query/user/` | 有返回，但给的是 `user_uid`（数字，如 `2486467579353139`），**不是 sec_uid** |
| `/aweme/v1/web/im/user/info/` | `url doesn't match` |
| 纯 HTTP 打开 `/user/self` | 返回 72KB 的**字节 JS 反爬验证页**（`_$jsvmprt`），HTML 里搜不到任何用户字段 |
| `user/profile/other/?user_id=数字uid` | `status_code=3170`，user 对象全 null |

⚠️ 注意 `query/user` 返回的 `user_uid` **会随登录状态变化**：
游客态是设备级 id（`2486467579353139`），登录后才是账号 uid（`101518012740`）。
所以它也不能当"登录成功"的证据——要看 `profile/self` 的 `status_code`。

### 17.2.1 喜欢：完全可用（2026-10-26 实测）

```
GET /aweme/v1/web/aweme/favorite/?sec_user_id={自己的}&count=20&max_cursor={cursor}
    + webSign
```

| 项 | 值 |
| --- | --- |
| 响应 | 1.7–2.1 MB / 页，`aweme_list` 19–20 条 |
| 翻页 | 用**响应里的 `max_cursor`** 当下一次的 `max_cursor`（不是页码 × 条数！） |
| 停止 | `has_more=0` |
| 实测 | 3 页共 58 条，id 无重复 |

第一版踩的坑：把 `max_cursor` 当成 offset 传 `page*20`，结果第 2 页返回和第 1 页一模一样。
`max_cursor` 是个**毫秒时间戳**（如 `1791887775000`），必须从响应里取。

### 17.2.2 收藏：两个接口，先拿夹子再拿作品（2026-10-26 实测）

**第一步，收藏夹列表**：

```
GET /aweme/v1/web/collects/list/?count=20&cursor=0   + webSign
→ {"collects_list":[{"collects_id_str":"7555198150416439040","collects_name":"1","total_number":219}],
   "has_more":false,"cursor":1,"status_code":0}
```

**第二步，夹子里的作品**：

```
GET /aweme/v1/web/collects/video/list/?collects_id=7555198150416439040&count=10&cursor=0   + webSign
→ HTTP 200，881 KB，aweme_list 10 条
```

注意参数名是 **`collects_id`**（带 s）。传 `collect_id` 会返回 `aweme_list: null`（不报错，就是空）。

网上流传的 `/aweme/v1/web/aweme/listcollection/` 是错的，回 `404 Unsupported path(Janus)`；
`collects/list` / `collects/video/list` 这套才是真的。

### 17.2.3 平台标签（video_tag）：推荐流里没有，详情接口 100%

用户想让"推荐倾向"用平台标签而不是作者标签。实测：

| 数据源 | 覆盖率 | 样本 |
| --- | --- | --- |
| 推荐流 `module/feed` 的 `video_tag` | **0 / 29 = 0%** | 29 条全 null |
| 详情 `aweme/detail` 的 `video_tag` | **17 / 17 = 100%** | 18 条里 17 条成功取到详情 |
| 同一批详情的 `text_extra`（作者标签） | 15 / 17 = 88% | — |

**耗时**：18 条详情用 10.2 秒，**平均 602 ms/条**（含 350ms 主动间隔）。
所以 40 条约 25 秒、100 条约 60 秒。

平台标签是**三级分类**，质量远高于作者标签：

```
美食 / 美食探店 / 餐厅探店
随拍 / 生活记录 / 日常vlog
人文社科 / 人文艺术 / 历史
游戏 / 竞技游戏
二次元 / 二次元内容 / 动漫IP
```

**结论：可行，而且比手工词表准。** 代价是必须逐条取详情（推荐流里拿不到）。
实现上应该"平台标签优先、作者标签兜底"——详情失败的那 5% 还能用作者标签补。

### 17.3 ⚠️ 根因：WebView2 的 sessionid 是会话 Cookie，重启就没了

这是这轮最重要的发现，解释了两个"怎么都抓不到"的老问题。

```
data/WebView2/EBWebView/Default/Network/Cookies 里查：
  .douyin.com  sessionid  95B  过期 2026-10-25   ← 会话 Cookie
```

`sessionid` 没有真正的过期时间（Chromium 记成"会话级"），
**WebView2 进程一退出，Cookie 就没了**。
于是内置浏览器每次重新打开都是**游客态**：

```
--capture-search → 打开搜索页 → 页面显示"登录"→ 搜索接口 2483 → 抓不到任何请求
--capture-fav    → 打开自己主页 → 页面显示"登录后即可观看喜欢、收藏的视频" → 不发 favorite 请求
```

解法：**把 session.json 里的登录 Cookie 反向注入回 WebView2**
（`App/WebCookieInject.cs`，用 `CoreWebView2CookieManager.AddOrUpdateCookie` 逐条写）。

- 只注入登录凭据，**不碰 webid / ttwid / s_v_web_id**，所以不会造成设备漂移
- 注入后 `CookieManager.GetCookiesAsync` 能读回 63 条、`document.cookie` 里能看到 sessionid
- 但**服务端仍然可能不认**——见 17.4

### 17.4 登录态判定：别再拿"能不能读评论"当健康标准

2026-10-26 实测的完整对照（同一份 Cookie）：

| 接口 | 返回 | 能说明什么 |
| --- | --- | --- |
| 评论 `comment/list` | 20 条 | **不能**说明登录——游客也能看评论 |
| 作者主页 `aweme/post` | 20 条 | **不能**说明登录——公开数据 |
| 推荐流 `module/feed` | 正常 | **不能**说明登录——游客也有推荐 |
| `user/profile/self` | `status_code=8` | **能**说明未登录 |
| 点赞 `commit/item/digg` | `status_code=0` 但状态不变 | 不可靠（风控会静默丢弃） |
| WebView2 打开 `/user/self` | 页面显示"未登录" | **能**说明未登录 |

所以 `VerifyLoginAsync` 改成：**主探针用 `profile/self`**（回 8 就是未登录），
点赞探针降级为兜底。以前只用点赞探针，风控挡了也返回 0，就一直误报"正常"。

**当前账号状态（2026-10-26 01:04 重新登录后）**：`profile/self` 返回 0 + 完整用户对象，
喜欢/收藏全部可用。**上一次登录在 10-26 00:27 前后就已失效**（那份 session.json
测 `profile/self` 回 8），但旧版本用"评论能不能读"判断，一直显示"正常"，没人发现。

⚠️ 这解释了用户为什么觉得"改代码之前正常"：**变的是显示，不是登录**。
旧逻辑（评论探针）把失效的登录判成正常；新逻辑（profile/self）如实报了出来。
